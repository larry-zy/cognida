## Context

Link 项目采用 Go + Python 异构架构，Go 服务负责 Agent 编排和存储，Python 服务提供文档处理、评测等增强能力。当前 Python 服务已有文档解析 (50051) 和评测服务能力，但缺乏数据分析能力。

数据分析是 Link 实现"AI 数据专家"定位的核心能力之一，Agent 需要通过数据分析来：
- 理解数据特征 (描述统计)
- 发现数据模式 (趋势分析)
- 生成洞察结论 (自动洞察)

**当前状态**:
- Python 服务已运行在端口 50051
- 已有 `services/document/` 和 `services/evaluation/` 模块
- gRPC 框架已就绪，可扩展新服务

**约束**:
- 必须遵循现有 Clean Architecture 分层规范
- 新服务通过 gRPC 暴露，Go 调用
- 遵循 Python 服务类型注解、异常处理、异步编程规范

## Goals / Non-Goals

**Goals:**
- 在 Python 服务中实现数据分析核心能力
- 提供数理统计、趋势分析、洞察发现三类功能
- 通过 gRPC 暴露服务，支持 Go Agent 调用

**Non-Goals:**
- 不实现数据存储 (使用现有 MySQL/Milvus)
- 不实现 NL2SQL (由 Go Agent 负责)
- 不实现可视化输出 (后续版本支持)
- 不实现实时流处理 (仅批处理分析)

## Decisions

### 1. 独立 gRPC 服务端口

**决策**: 数据分析服务使用独立端口 50053，而非复用 50051。

**理由**:
- 关注点分离：文档处理 vs 数据分析
- 独立扩展：可根据负载独立扩容
- 故障隔离：一个服务故障不影响另一个

**替代方案**: 复用 50051 端口 - 被拒绝，会导致服务职责不清

### 2. 使用 pandas/numpy 作为数据处理基础

**决策**: 使用 pandas DataFrame 作为核心数据结构。

**理由**:
- 行业标准，生态成熟
- 内置丰富统计函数
- 与 numpy/scipy 无缝集成
- 支持向量化操作，性能好

**替代方案**: 纯 numpy 数组 - 被拒绝，缺乏列名等语义信息

### 3. 统计算法选择

| 功能 | 库选择 | 理由 |
|------|--------|------|
| 描述统计 | pandas/scipy | 内置函数，性能好 |
| 正态检验 | scipy.stats (shapiro, kstest) | 标准实现 |
| 线性回归 | scipy.stats.linregress | 简单高效 |
| 季节分解 | statsmodels.tsa.seasonal_decompose | 经典 STL 算法 |
| 异常检测 | scikit-learn IsolationForest | 无需假设分布 |

### 4. 洞察生成策略

**决策**: 采用规则 + 统计的组合方法，不依赖 LLM。

**理由**:
- 确定性输出，便于测试
- 计算成本可控
- LLM 可作为后续增强层

**架构**:
```
原始数据 → 统计计算 → 规则引擎 → 洞察输出
              ↓
         阈值判断
```

## Risks / Trade-offs

### Risk 1: 大数据集性能

**风险**: pandas 在内存中处理，大数据集可能 OOM。

**缓解**:
- 添加数据量检查 (默认限制 10万行)
- 支持分块处理
- Go 端预聚合后再调用

### Risk 2: 统计假设不满足

**风险**: 部分统计方法有假设前提 (如正态分布)，实际数据可能不满足。

**缓解**:
- 实现多种检验方法
- 返回检验结果，让 Agent 判断
- 文档中说明适用条件

### Risk 3: 时序数据处理

**风险**: 趋势分析依赖时序数据，输入可能不是时间序列。

**缓解**:
- 自动检测时间列
- 非时序数据返回错误提示
- 提供时序预处理建议

### Trade-off: 准确性 vs 性能

**选择**: 优先准确性，使用科学计算库而非近似算法。

**影响**: 计算时间可能较长，通过超时控制 (默认 30秒)。
