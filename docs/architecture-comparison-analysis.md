# 架构对比分析：V4 vs 当前 Clean Architecture

## 一、本质对比

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         架构方案对比                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  V4 方案（三层分类）                                                        │
│  ────────────────────────────────────────────────────────────────────────  │
│  Business      ←→ Domain + Application                                      │
│  Capability    ←→ Application + Infrastructure                              │
│  Infrastructure ←→ Infrastructure                                           │
│  Handler       ←→ Interface                                                │
│                                                                             │
│  当前 Clean Architecture                                                    │
│  ────────────────────────────────────────────────────────────────────────  │
│  Domain        ←→ 领域层                                                    │
│  Application   ←→ 应用层                                                    │
│  Infrastructure←→ 基础设施层                                                 │
│  Interface     ←→ 接口层                                                    │
│                                                                             │
│  结论: V4 方案本质上就是换了名字 Clean Architecture！❌                      │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 二、为什么"换汤不换药"？

### 2.1 分类标准对比

| 维度 | Clean Architecture 分类 | V4 分类 | 问题 |
|------|----------------------|---------|------|
| 按技术分层 | ✅ Domain/App/Infra | ❌ Business/Capability/Infra | 都是按技术分层 |
| 按业务领域 | ❌ 跨领域分散 | ❌ 同样跨领域 | 没有解决 |
| 依赖方向 | ✅ 清晰 | ✅ 清晰 | 相同 |
| 层间转换 | ❌ 多次转换 | ❌ 多次转换 | 没有改善 |

### 2.2 映射关系

```
【RAG 的归属】

Clean Architecture:
├── domain/rag/          # 领域定义
├── application/usecases/rag/  # 用例
└── infrastructure/rag/  # 实现

V4 方案:
├── business/           (没有 rag，因为不是业务)
├── capability/rag/     # 能力层
└── store/              # 基础层

本质上是一样的：
- domain/rag ≈ capability/rag（类型定义）
- application/usecases/rag ≈ capability/rag（实现）
- infrastructure/rag ≈ store/（数据访问）
```

## 三、真正的问题是什么？

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           核心问题分析                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  问题 1: 分层只是组织形式，不能减少跨层调用                                  │
│  ────────────────────────────────────────────────────────────────────────  │
│  不管叫 Domain 还是 Business，不管叫 Application 还是 Capability：          │
│  - 简单的 CRUD 仍然要跨越 Handler → Service → Repository                   │
│  - 复杂的 RAG 仍然要跨越更多层级                                             │
│                                                                             │
│  问题 2: 分类标准不统一                                                      │
│  ────────────────────────────────────────────────────────────────────────  │
│  - Agent 既是业务又是能力（对外是业务，对内是能力）                          │
│  - RAG 是能力但又是某些模块的核心逻辑                                       │
│  - LLM 是能力但被所有模块依赖                                                │
│                                                                             │
│  问题 3: 换名字不换本质                                                      │
│  ────────────────────────────────────────────────────────────────────────  │
│  - Business ≠ Domain + Application 的实际效果相同                            │
│  - Capability ≠ Application + Infrastructure 的实际效果相同                   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 四、为什么换名字？

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           换名字的原因                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  原因 1: "Domain" 在 AI 系统中概念模糊                                       │
│  ────────────────────────────────────────────────────────────────────────  │
│  - 传统系统: Domain = 业务规则（如订单、支付）                               │
│  - AI 系统: Domain = ???（Agent 是业务还是能力？）                           │
│                                                                             │
│  原因 2: "Application" 层职责混乱                                            │
│  ────────────────────────────────────────────────────────────────────────  │
│  - usecases 和 services 重复                                                 │
│  - 想用 "Capability" 强调这是可复用能力                                      │
│                                                                             │
│  原因 3: 想找到"银弹"                                                        │
│  ────────────────────────────────────────────────────────────────────────  │
│  - 以为换个名字就能解决架构问题                                               │
│  - 实际上问题在过度分层，不在名字                                             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 六、最终建议

### 6.1 不推荐大规模重构

| 方案 | 成本 | 风险 | 收益 | 推荐 |
|------|------|------|------|------|
| 保持 Clean Architecture + 修复违规 | 低 | 低 | 中 | ✅ |
| 重命名为 V4 架构 | 中 | 中 | 小 | ❌ |
| 推倒重来 | 高 | 高 | 不确定 | ❌ |

### 6.2 具体行动计划

```
Sprint 1-2: 修复违规
├── 添加架构测试，禁止新违规
├── 修复 47 处 Application → Infrastructure 违规
└── 删除适配器

Sprint 3-4: 合并重复
├── 合并 usecases 和 services
├── 删除重复的 Repository 接口
└── 删除空目录

Sprint 5-6: 简化转换
├── Handler 直接使用 Service 类型
├── Service 直接使用 Domain 实体
└── 删除中间 DTO

Sprint 7-8: 评估效果
├── 性能测试
├── 代码审查
└── 决定是否继续优化
```

**核心观点**: V4 方案只是换了个马甲，真正需要做的是修复违规、合并重复、简化转换，而不是推倒重来。
