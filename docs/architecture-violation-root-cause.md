# 架构违规根因分析与解决方案

> 问题：架构规则很好，但执行时不去遵守

## 一、问题本质

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           问题本质分析                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  现象:                                                                     │
│  ────────────────────────────────────────────────────────────────────────  │
│  • 架构文档写得很详细                                                       │
│  • CLAUDE.md 规范很清晰                                                     │
│  • 但实际代码有 34 处违规（2026-05-30 检测）                                                   │
│                                                                             │
│  根因:                                                                     │
│  ────────────────────────────────────────────────────────────────────────  │
│  1. 写代码时"图方便"直接违反规则                                             │
│     • 为了省事，直接 import infrastructure                                  │
│     • 不想写接口，直接用具体类型                                              │
│     • 加功能时偷懒，不走正确流程                                             │
│                                                                             │
│  2. 缺少强制检查机制                                                        │
│     • 没有自动化检测违规的工具                                               │
│     • Code Review 没有检查架构违规                                           │
│     • CI 没有架构测试                                                       │
│                                                                             │
│  3. 架构文档和实际开发脱节                                                   │
│     • 文档写好了，但开发者不看                                                │
│     • 或者看了，但觉得"这个情况特殊"可以例外                                  │
│     │                                                                       │
│     └── "破窗效应"：一次例外，次次例外                                       │
│                                                                             │
│  结论:                                                                     │
│  ────────────────────────────────────────────────────────────────────────  │
│  这是**组织/流程问题**，不是技术问题                                          │
│  需要**工程手段**强制执行规则，而不是依赖文档                                 │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 三、为什么文档不够？

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           为什么文档没用？                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. 开发者不看文档                                                           │
│     ────────────────────────────────────────────────────────────────────  │
│     • 文档太长，没人仔细看                                                   │
│     • 或者根本不知道有这个文档                                               │
│     • 或者看了，但记不住                                                     │
│                                                                             │
│  2. 文档无法在写代码时提醒                                                    │
│     ────────────────────────────────────────────────────────────────────  │
│     • 写代码时文档不在眼前                                                   │
│     • 没有实时的违规提醒                                                    │
│     • 编译器不会报错                                                         │
│                                                                             │
│  3. 文案没有强制力                                                           │
│     ────────────────────────────────────────────────────────────────────  │
│     • 文档只是建议，不是强制                                                 │
│     • "这次特殊情况"可以例外                                                  │
│     • 没有人因为违反文档而承担后果                                           │
│                                                                             │
│  结论:                                                                     │
│  ────────────────────────────────────────────────────────────────────────  │
│  ❌ 文档不能解决问题                                                        │
│  ✅ 需要自动化工具强制执行规则                                               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

    pkgs, err := packages.Load(&packages.Config{
        Mode: packages.NeedImports | packages.NeedFiles,

    for _, pkg := range pkgs {

            if contains(imp, "internal/infrastructure") {

                    pkg.PkgPath,
                    imp,
                )
            }
        }
    }

#### 工具 2: Pre-commit Hook

```bash
# .git/hooks/pre-commit

#!/bin/bash

echo "🔍 Running architecture tests..."

# 运行架构测试
go test ./test/architecture_test.go

if [ $? -ne 0 ]; then
    echo "❌ Architecture tests failed!"
    echo "Please fix architecture violations before committing."
    exit 1
fi

echo "✅ Architecture tests passed"
```

#### 工具 3: CI 检查

```yaml
# .github/workflows/architecture-check.yml

name: Architecture Check

on:
  pull_request:
    paths:
      - 'internal/**'
      - 'test/architecture_test.go'

jobs:
  architecture:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-go@v4
        with:
          go-version: '1.21'

      - name: Run architecture tests
        run: go test -v ./test/architecture_test.go

      - name: Fail on violations
        if: failure()
        run: |
          echo "❌ PR contains architecture violations!"
          echo "Please fix before merging."
          exit 1
```

### 4.4 依赖分析工具

```go
// cmd/deps-analyzer/main.go

package main

// 简单的依赖分析工具
// 扫描代码库，生成依赖关系图
// 标记出违反规则的依赖

func main() {
    analyzer := NewArchitectureAnalyzer()
    
    // 定义规则
    analyzer.AddRule(Rule{
        From: "internal/application",
        CannotImport: []string{"internal/infrastructure"},
    })
    
    analyzer.AddRule(Rule{
        From: "internal/interface",
        CannotImport: []string{"internal/infrastructure"},
    })
    
    // 分析
    violations := analyzer.Analyze("internal/")
    
    // 报告
    for _, v := range violations {
        fmt.Printf("❌ %s imports %s\n", v.From, v.Import)
    }
    
    if len(violations) > 0 {
        os.Exit(1)
    }
}
```
