## ADDED Requirements

### Requirement: 独立操作计划与最小权限
受控写入与 ETL SHALL 使用独立于默认只读分析的持久任务入口，固定输入版本、受管派生目标、SQL 或代码摘要、预估影响及有效期；MUST 由服务端授予最小 scope，复用现有工具和审计，禁止修改外部数仓或原始业务表，脚本执行遵守 Sandbox 契约。

#### Scenario: 分析请求要求修改外部来源
- **WHEN** 默认分析会话或操作计划尝试写入外部数据源、原始表或无归属的派生目标
- **THEN** 系统拒绝执行并记录拒绝原因，不提升会话 scope、不改写目标路由，也不创建虚假的成功操作记录

### Requirement: 确认绑定与执行前复查
操作确认 MUST 绑定 tenant、user、action、计划版本、内容 hash 和有效期，不能由 Agent 自行批准；执行前 SHALL 复查权限、目标归属及数据前置条件，任何影响范围或操作内容变化均须新计划版本与重新确认。

#### Scenario: 确认后内容变化或权限撤销
- **WHEN** 已确认计划的 SQL、输入、目标或预期版本发生变化，或执行者权限已撤销、确认已过期
- **THEN** 系统拒绝使用旧确认执行，保留原审批证据并请求重新审核；跨用户或跨租户重放确认同样被拒绝

### Requirement: 提交幂等与结果核对
操作 MUST 以确定性 ID 和请求摘要约束幂等，数据库支持事务时将 DML 与幂等记录一致提交，其他流程持久化分阶段回执；提交响应丢失 SHALL 进入待核对状态并查询实际提交结果，不得盲目重放写入，同键不同内容必须冲突。

#### Scenario: 提交成功后回执丢失
- **WHEN** 数据库已完成提交，但任务未收到回执便重启或同一请求被重复投递
- **THEN** 恢复流程通过操作 ID 与提交记录查证，返回原结果且不重复修改数据；无法判定时保持待核对，不宣称失败后直接重写

### Requirement: 取消与补偿边界
取消 SHALL 区分尚未执行、执行中、已提交和结果未知，停止未开始步骤并对在途执行发出有界取消；MUST 保留已提交影响和核对状态，声明事务回滚、派生版本切换或补偿能力，不把取消请求等同于已经撤销数据，也不让迟到成功覆盖取消决定。

#### Scenario: 用户在提交临界点取消
- **WHEN** 用户取消操作时数据库提交结果尚不明确
- **THEN** 系统停止后续步骤并核对原操作，明确展示取消请求与实际已提交影响；仅在支持且获授权时补偿，不通过重新执行原写入完成核对

### Requirement: ETL 先生成新版本再切换
ETL MUST 在租户拥有的受管派生空间生成独立候选对象，校验类型、行数、来源和摘要后才切换活动版本，禁止先删除旧目标再执行可能失败的建表；切换及清理 SHALL 可恢复且仅作用于本任务对象，失败或取消保留原活动版本。

#### Scenario: 候选生成或切换期间失败
- **WHEN** 新派生表计算失败、任务取消，或活动版本切换的回执丢失
- **THEN** 系统保留旧活动数据，依据持久回执核对是否已切换后再恢复或清理，不删除其他任务对象；支持的回退只切换明确保留的版本并留下审计记录
