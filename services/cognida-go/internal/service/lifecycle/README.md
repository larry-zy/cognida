# Lifecycle service

The authenticated `/api/v1/lifecycle` API runs seven typed specialists independently or through registered, versioned templates. The initial `web-knowledge-to-insight` template is access → quality → cleaning → enrichment → publication → analysis → evaluation. Clients cannot submit a DAG or tool list. Direct Collection APIs remain available and ingestion can enter the lifecycle through the source resolver. This implementation supersedes the unimplemented collection-agent-swarm architecture.

## Persistence and authorization

Apply paired migration `000008_add_data_lifecycle` with the normal `cmd/migrate-db up` command before starting workers. Definitions, references, runs, stages, approvals and progress events use MySQL; raw snapshots and reports use the configured object store. Each queue message contains only tenant and stage IDs. Redis must use its own `lifecycle` namespace because dispatchers only know their registered job types.

A reference is an immutable `asset_id` UUID plus positive `version`; `asset_ref_id` serializes it as `UUID:version`. Derived snapshots keep parent references and advance the lineage version. Resolution reloads canonical tenant metadata, checks policy/expiry and verifies the stored content hash. Caller-supplied object keys or policy snapshots are never accepted by the HTTP API. `Config.Authorize` must consult current tenant membership: members may read/invoke, administrators resolve approvals, and sensitive references require the sensitive scope. Publication always pauses for administrator approval, as do LLM/high-cost operations. Recommendations cannot change source sensitivity or authorize publication.

All POST creation endpoints require `Idempotency-Key`; repeat requests resolve to the existing resource and conflicting input returns 409. Imports preserve content identity; retries cannot overwrite immutable content. API lists return `{items,next_cursor,has_more}` and use UUID cursors for runs/invocations and compound `UUID:version` cursors for assets. Stage state includes `waiting`, `queued`, `running`, `awaiting_approval`, `succeeded`, `failed`, `cancelled` and `quarantined`.

## Execution and recovery

The service worker uses the generic leased Redis queue and MySQL attempt fences. Every ten seconds it reconciles unfinished runs, expires pending approvals and requeues durable work, including a crash after stage completion but before scheduling successors. Approval expires after 24 hours. Stage retries are bounded; a failed run can explicitly retry failed stages while retaining successful immutable outputs. Gate failures are routed only through explicitly permitted edges; failed cleaning quarantines descendants. Cancellation persists first and cancels running adapters when observed; attempt/status fences prevent stale workers from committing output.

Register the standalone agents with `Service.RegisterAgents`. Their command envelopes accept references/options and return durable task handles, not raw source content. The Pipeline Orchestrator exposes template/proposal/start/inspect/cancel/approval-inspection commands only. The existing conversational Data Agent keeps its ID/API aliases and is labeled Data Analysis; its default tool groups omit operation tools. The new lifecycle Analysis expert requires published approved references. Explicit Data Operation tools remain governed by the existing operation scope and confirmation system.

## Compute and publication configuration

`NewHTTPCompute` calls the configured internal Python evaluation HTTP service (`/api/v1/lifecycle/profile`, `/clean`, `/enrich`) using `INTERNAL_HTTP_AUTH_TOKEN` and propagated request IDs. Missing compute credentials/configuration fail clearly. Input limits mirror Python: text 200,000 characters; tables up to 200 columns, 10,000 rows, 100,000 cells and 4 MiB. The composition root provides `AccessFunc` for authorized web/knowledge/datasource/result acquisition and `PublishFunc` for durable KB or catalog publication. Both must return provenance/durable receipts and preserve source authorization. Publication adapters must be idempotent because delivery is at least once.

The Analysis expert produces reproducible descriptive statistics with evidence references and a decision envelope. Evaluation verifies artifact integrity/provenance; neither claims semantic correctness, causality or model accuracy without labelled evidence. Confidence is null when no calibrated estimate exists.

## Verification and operation

Unit tests cover contracts, reference serialization, protected options, HTTP compute authentication and statistics. Integration tests use real MySQL plus a random Redis namespace, test a seven-stage run, approval, tenant isolation, idempotency, fan-in, retries, cancellation fences, restart recovery and authenticated HTTP/SSE. They never flush Redis or create schema with AutoMigrate. Set `MYSQL_DSN` to an isolated migrated database and run `go test -tags=integration ./internal/service/lifecycle ./internal/handler -run TestLifecycle`. To also exercise Python, set `LIFECYCLE_TEST_PYTHON_URL` and `LIFECYCLE_TEST_TOKEN` to a temporary authenticated compute API; stop it after testing.

Observe `/runs/:id/events` for request, run, stage and approval events. The SSE endpoint honors `Last-Event-ID`; clients can reconnect without reexecuting work. Before rollback, stop API/worker admission, finish or cancel active runs, and preserve object-store snapshots. Rolling migration 8 down deletes lifecycle metadata and must only be used after explicit backup/retention decisions. Legacy Collection and chat data are unaffected by these lifecycle tables.


## First-release collaboration and trust boundaries

Durable stage delegation uses the validated DAG and the same seven typed adapters as standalone invocation. DAG acyclicity, at most 32 stages, declared input/output kinds, bounded attempts and startup-only templates replace recursive LLM delegation; no stage can acquire another specialist’s tools. Registry invocation still uses the existing agent/collaboration registry and returns compact task/reference envelopes. Collection artifacts, tenant-authorized parsed KB documents (including existing file/OCR ingestion), datasource snapshots with catalog coordinates, owner-checked session results and evaluation records enter through `SourceRequest`; this release reuses existing upload/connector parsers rather than adding a parallel file ingestion path.

Every stage execution opens the existing OpenTelemetry orchestration span with tenant/user, request, job, run, stage and agent identifiers. Its final status and output refs are correlated with durable stage events. `Config.Audit`, wired to the existing asynchronous audit writer, records asset resolution, acquisition, approval attempts and stage/publication outcomes without raw bodies or credentials. The normal audit writer capacity and best-effort delivery semantics still apply. Admin approval and explicit Data Operation confirmation remain separate boundaries.

Conversational Analysis exposes `verify_results` and `decision_synthesize` through the analytics group; its Analysis specialist gains no SQL tools. Verification accepts two distinct same-session result refs and explicit key/value columns, with bounded exact decimal absolute/relative tolerance checks. Duplicate keys are rejected; missing/null/non-numeric or unsafe-precision values require clarification. Agreement is never represented as proof of independent paths or correct business semantics. This is the constrained equivalent of the roadmap’s semantic/lexical dual-path check: callers obtain both results under existing permissions, and the verifier never launches extra SQL. Redis exact reads preserve number tokens; already-rounded large floating-point values are marked unverifiable.

Decision synthesis resolves immutable authorized Insight refs, optionally reruns verification and retrieves actual evidence through the existing scoped RAG API. It returns cited insights, knowledge excerpts and a DecisionCard; proposed actions stay unverified hypotheses requiring human review. Conflicting numbers block adoption pending clarification. It does not silently execute actions or invent confidence/calibrated success likelihoods. A/B evaluation and adaptive retrieval/chunking use their separate services; neither toggles production configurations automatically.
